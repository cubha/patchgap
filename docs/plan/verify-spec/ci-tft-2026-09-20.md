# VERIFY-SPEC — TFT 정기 수집 CI (ST1~ST4, 2026-09-20)

## 구현 결정

- **캘린더 상수를 `src/pipeline/collect/`로 승격**했다(ST1). `scripts/run-tft-collect.ts`는 재수출로
  호환을 유지한다 — 워크플로 `determine` 스텝이 같은 상수를 읽어야 하는데, 스크립트 안에 있으면
  CI가 규칙을 다시 적게 되고 두 곳이 조용히 갈라진다.
- **`determine`을 heredoc이 아닌 실파일(`scripts/tft-determine.ts`)로 썼다.** LoL `collect.yml`은
  임시 `.ts`를 heredoc으로 만들어 실행하고 지우는데, 그 코드는 tsc·eslint·vitest 어느 게이트도
  보지 못한다. 수집 실행 여부를 정하는 코드가 검증 밖에 있는 셈이라 답습하지 않았다.
  **`collect.yml`은 건드리지 않았다**(9/24 무인 실행 보호).
- **표본 대기(`TFT_MIN_LIVE_DAYS=7`)를 새로 넣었다.** 계획에 없던 항목이다 — 구현 중 실측으로
  필요성이 드러났다: KR Master+ 래더는 하루 약 227매치(18.2 = 11일에 2,496)라 패치 당일 수집은
  새 구간이 비어 판정이 전부 표본부족으로 떨어진다. LoL(하루 1만)의 cron 설계를 그대로 가져오면
  TFT에서만 조용히 빈 판정이 쌓인다.
- **스테일 임계(`TFT_STALE_AFTER_DAYS=22`)로 명세를 정정했다.** 최초 규칙("열린 창 + 산출물 있음")은
  **정상 정상상태를 매일 경보**했다(패치 직후부터 다음 패치까지가 전부 그 상태다). 관측 주기
  15일의 1.5배를 넘을 때만 경보한다. ⚠️ **테스트를 고쳤다** — 통과시키려는 목적이 아니라 명세가
  틀렸기 때문이며, 이 결정은 사용자에게 명시 보고했다.
- **키가 LoL과 다르다는 것을 실측으로 확인**하고 `RIOT_TFT_API_KEY`를 새 시크릿으로 분리했다.
  이건 계획 §3-⑤를 실측이 확장한 것이다.

## 미확인 사항 (critic 최고 신호원)

1. **워크플로가 실제로 도는지 아직 모른다.** `verify.sh`는 YAML을 보지 않는다. `workflow_dispatch`
   실행은 파일이 **기본 브랜치에 있어야** 가능하므로 머지 후에 해야 한다 — 이 SPEC 시점에는 미수행.
2. **`RIOT_TFT_API_KEY`는 24시간 개발 키다.** 등록한 값은 내일 만료된다. 즉 제품 승인 전까지
   무인 실행은 **구조적으로 불가능**하고, 배선은 "승인되는 날 바로 도는 상태"로만 완성된다.
   프리플라이트가 그 기간 동안 빨간 X 대신 경고를 남긴다.
3. **`run-tft-collect.ts`가 `--target`만 받고 패치를 안 받는다.** 크롤러가 `TFT_PATCH_WINDOWS`
   전 구간을 한 번에 돈다. 18.3이 추가되면 3개 창을 도는데, `ids-seen.txt`가 재방문을 막으므로
   증분만 든다 — **그러나 CI 캐시가 비면 전량 재수집**이 된다(실측 6,145초). 캐시 키를
   `to` 패치로 잡았고 `restore-keys` 폴백을 뒀지만 GitHub 캐시는 7일 미사용 시 소멸한다.
4. **18.3이 실제로 9/24에 나올지는 추정**이다(간격 15일 1회 관측). 빗나가면 표본 대기 계산도
   함께 밀린다 — 캘린더가 수기라 사람이 갱신해야 하고, 그 누락은 22일 뒤 경고로만 잡힌다.
5. **일 1회 cron의 프리플라이트 비용**은 하루 1콜이라 무시 가능하나, 제품 미승인 기간 내내
   매일 경고가 쌓인다. 노이즈로 느껴지면 cron을 주 1회로 줄이는 선택지가 있다.
